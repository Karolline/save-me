# 공고 매칭 규칙

`job-analyst`가 공고를 분석할 때 따르는 절차와 판정 기준. 절대 규칙(없는 경험·수치를 만들지 않는다 등)은 이 파일이 아니라 `.claude/agents/job-analyst.md` 본문에 있다. 분석을 적는 양식은 [`docs/job-inbox.md`](../job-inbox.md)이고, 이 파일은 "무엇을 어떻게 판단하는가"만 다룬다.

경험·이력은 DB에서 `agent_read` 조회 명령으로 읽는다 (`backend/` 안에서 `uv run python -m app.agent_read ...`). 파일로 된 경험 DB는 없다.

## 절차

1. 입력 확인: 공고 원문(텍스트) 또는 URL. 모자라면 추측하지 말고 무엇이 없는지 보고하고 끝낸다.
2. 먼저 `profile`(입사 가능 시기, 근무지, 희망 직무, 커리어 방향, 기술 스택), `experience-index`(경험 목록, 태그 어휘, 행동질문 매핑), `jobs`(이미 한 분석인지)를 본다.
3. 공고에서 요구사항을 뽑는다. 주요업무, 자격요건, 우대사항을 구분하고, 공고 문장은 그대로 옮긴다.
4. 후보로 좁힌 경험만 `experience <ID>`로 열어 각 요구사항에 매칭한다. 근거는 `상황/과제/행동/결과` 본문에서만 가져온다. 근거 경험은 `근거 경험:` 줄에 경험 이름(또는 ID)으로 적는다.
5. 공고가 요구하는데 경험이 비어 있으면 `[없음]`과 `근거 없음:`으로 쓰고 `갭`에 보낸다. 이력(경력·기술 스택)에는 근거가 있는데 경험으로 적혀 있지 않은 것은 갭이 아니라 `경험 보완 제안`(작성 권장)이다.
6. 핏 평가, 성향 적합도, 부각할 경험을 정한다 (아래 기준).
7. 회사 동향을 조사한다 (아래 기준).
8. `docs/job-inbox.md` 양식 그대로 `private/inbox/jobs/YYYY-MM-DD-<회사>-<직무>.md`에 쓴다. `공고 원문`은 맨 끝에, 받은 그대로.

## 공고를 URL로 받았을 때

1. `WebFetch`로 본문을 가져온다. 프롬프트에 "요약하지 말고 공고 전문을 그대로 추출하라"고 명시한다. WebFetch는 작은 모델로 내용을 추려 답하므로, 그냥 요청하면 요약본이 돌아와 자격요건이 빠진다.
2. 가져온 본문을 `공고 원문`에 넣고, 맨 위에 `※ WebFetch 추출본 (원문과 다를 수 있음)`을 적는다. URL은 `공고 URL`에 적는다.
3. 가져오기에 실패하거나 내용이 부실하면 추측해 채우지 말고 멈춘다. 실패했다고, 무엇이 비었는지 보고하고 본문 붙여넣기가 필요하다고 돌려준다. 회사명과 직무만으로 자격요건을 지어내면 존재하지 않는 요구사항에 맞춰 경험을 고르게 된다.
4. 자주 실패하는 유형: 로그인이 필요한 페이지, JS로 그리는 채용 사이트, PDF·이미지 공고. 일부만 가져와졌으면 어느 항목이 비었는지 알린다.

## 핏 평가 기준

자의적으로 매기지 않는다. 공고끼리 나중에 비교할 수 있도록 3단계를 유지하고, `85% 매칭` 같은 가짜 정밀도를 쓰지 않는다.

| 등급 | 기준 |
|---|---|
| 상 | 자격요건 대부분에 경험 근거가 있고, 핵심 기술 스택이 일치한다 |
| 중 | 자격요건 절반 이상을 충족하나 일부 갭이 있다. 갭을 인접 경험으로 연결해 설명할 수 있다 |
| 하 | 핵심 요구 역량에 근거가 없다. 지원하려면 새 학습이나 포장이 필요하다 |

`profile`의 입사 가능 시기, 근무지 같은 조건도 함께 확인한다. 기술 핏이 `상`이어도 입사 시기가 맞지 않으면 그 사실을 `지원 조건`과 `확인 필요`에 쓴다. `profile`에 없는 조건은 짐작하지 말고 `[확인 필요]`로 둔다.

판정 근거는 `## 핏 평가`에 "판정 근거: 자격요건 5개 중 3개 충족, 2개 부분."처럼 센 숫자와 함께 쓰고, 빈 곳을 한 줄로 적는다.

## 성향 적합도 (Culture & Work-Style Fit)

기술 핏과 별도 축이다. 기술 핏은 "붙을 수 있는가", 성향 적합도는 "가서 맞는가"를 본다. 모든 공고 분석에 포함한다. 판정 기준은 `profile`의 커리어 방향과 희망 직무다. 이 칸이 비어 있으면 아래 루브릭을 일반 기준으로만 적용하고 `확인 필요`에 "커리어 방향이 비어 있어 성향 판정이 일반 기준"이라고 쓴다.

### 점수는 루브릭으로만 매긴다

100점은 아래 4개 항목의 합이다. 인상으로 점수를 매기지 않는다. 각 항목 점수 옆에 근거가 된 공고 문구를 인용한다(`공고 근거:`). 공고에 언급이 없으면 추정해서 점수를 주지 않고 0점 + `공고에 언급 없음`으로 적는다.

| 항목 | 배점 | 만점 조건 |
|---|---|---|
| 비즈니스 성과 연계 | 30 | 매출·비용·비즈니스 문제 해결이 업무 목적으로 명시됨 |
| 현업 소통·데이터 편의성 | 25 | 마케팅·사업·기획 등 비기술 직군이 데이터 사용자/협업 대상으로 명시됨 |
| 도메인 데이터(DW/DM) 운영 | 25 | 도메인 지표 기반 DW/DM 구축·운영이 주 업무 |
| Red Flag 부재 | 20 | 아래 Red Flag 징후 없음. 징후 1개당 감점 |

| 판정 | 기준 |
|---|---|
| Green (적합) | 70점 이상 |
| Yellow (신중 검토) | 40~69점, 또는 공고 정보가 부족해 판단이 어려울 때 |
| Red (부적합) | 40점 미만, 또는 점수와 무관하게 실질 R&R이 순수 기술 연구·엔진 개발로 추정될 때 |

### Red Flag 징후 (순수 R&D 조직)

- 오픈소스 리서치, 분산 컴퓨팅 엔진 코어 개발, 컴파일러·스토리지 엔진 수준 작업이 주 업무
- 데이터의 사용자(현업)가 공고에 등장하지 않고, 플랫폼 자체가 목적으로 서술됨
- 기술 스택 나열이 업무 설명보다 길고, 운영 안정성·SLA 언급이 없음

플랫폼 구축 자체는 Red Flag가 아니다. 사용자의 지향점이 모던 데이터 플랫폼이므로, 현업이 쓰는 데이터를 위한 플랫폼은 적합으로, 플랫폼이 연구 대상인 조직만 기피로 본다.

### 적는 것

양식의 `## 성향 적합도`에 다음을 쓴다.

1. 등급, 총점, 실제 역할 유형(추정임을 `(추정)`으로 밝힌다)
2. `### 점수표`: 항목별 `받은 점수/만점`과 `공고 근거`
3. `### 잘 맞는 점`: 현업 소통, 비즈니스 성과 연계, 데이터 편의성과 일치하는 실제 업무 문구
4. `### 공고 행간 읽기`: 기술 키워드를 걷어냈을 때 월~금 실제 주 업무가 비즈니스 지표·마트 서포트인지 순수 기술 연구·인프라 구축인지. 추정임을 밝히고 근거 문구를 단다
5. `### Risk · Red Flag 체크`
6. `## 면접 역질문`에 1~2개: 이 조직이 비즈니스 기여형인지 R&D형인지 떠볼 질문 (예: 데이터 요청이 주로 어느 부서에서 오는지, 최근 분기 팀 성과를 어떤 지표로 평가했는지)

기술 핏이 `상`이어도 성향이 Red면 `한 줄 결론`이나 `핏 평가`에 함께 쓴다. 지원 여부는 사용자가 정한다 (`지원 여부: 미정`).

## 회사 동향 분석

공고만 보면 "무엇을 할 줄 아는가"까지만 맞출 수 있다. 회사가 지금 어디에 돈을 쓰고 무엇이 밀리는지 알아야 "그래서 지금 이 회사에 내가 필요하다"를 말할 수 있다. 모든 공고 분석에 포함한다. 적는 양식은 `docs/job-inbox.md`의 "회사 동향 쓰는 법"이다.

### 조사 항목

| # | 관점 | 볼 곳 | 정리할 것 |
|---|---|---|---|
| 1 | 요즘 어디에 돈을 쓰는가 | 최근 1년 뉴스, 회사 기술 블로그, 상장사면 DART 사업보고서 | 신사업·투자·인수·조직 개편, 기술 블로그에서 반복되는 주제. DART는 숫자를 다 옮기지 않는다: 이익이 나는지, 어느 사업부에서 나는지만 본다 |
| 2 | 경쟁사 대비 | 뉴스, 업계 기사, 점유율·순위 자료 | 주요 경쟁사 2~3곳을 정하고 앞서는 것과 밀리는 것을 나눠 적는다 |
| 3 | 실제 사용자 반응 | 앱스토어·플레이스토어 리뷰, 커뮤니티 글 | 반복되는 불만과 칭찬. 한두 건이 아니라 여러 번 나오는 것만 |
| 4 | 회사가 가는 방향 | 채용공고 자체(담당업무·우대사항·팀 소개), 1의 결과 | 이 포지션을 왜 지금 뽑는지. 공고 문구를 인용한다 |

B2B·비상장이라 2·3을 볼 자료가 없으면 `자료 없음`으로 적고 넘어간다. 억지로 채우지 않는다.

### 어필 포인트: "내가 필요하다"

1~4에서 나온 회사의 과제·약점·방향 각각에 내 경험이 어떻게 도움이 되는지 2~4개를 쓴다. 번호 하나가 하나이고, `회사 상황:` 아래에 `기여:`와 `근거 경험:`을 따로 쓴다.

- 근거 경험이 없는 어필 포인트는 쓰지 않는다. 회사에 필요해 보이지만 내 경험이 없는 것은 `어필 포인트로 쓰지 않은 것`과 `갭`에 보낸다.
- 어필 포인트는 자소서 지원동기·입사 후 포부, 면접 "왜 우리 회사?" 답변의 재료다. 작성자가 쓸 수 있도록 한 줄씩 구체적으로 쓴다.

### 사실 확인 규칙

- 조사는 `WebSearch`·`WebFetch`로 한다. 모든 사실 항목에 출처 이름·날짜·링크를 단다. 출처 없는 문장은 쓰지 않는다.
- 학습 지식만으로 회사 현황을 쓰지 않는다. 오래됐거나 틀린 정보가 면접장에서 그대로 나간다. 검색이 실패하면 그 항목은 내용을 `자료 없음`으로 쓰고 `조사 메모`에 실패했다고 밝히며, 사용자에게 알린다.
- 사실(출처 있음)과 해석을 구분한다. 해석은 `해석 (추정):`으로 쓴다.
- 오래된 자료의 ⚠ 표시는 쓰지 않는다. 앱이 조사일과 출처 날짜로 계산하므로 출처 날짜를 빠뜨리지 않는다.

## 부각할 경험 선정 규칙

최소 3개, 최대 5개. 공고와의 적합도 순으로 정렬한다.

- 화려한 순이 아니라 맞는 순이다. 가장 큰 프로젝트라도 공고가 다른 방향이면 뒤로 간다.
- 순위마다 대응하는 공고 요구사항을 명시한다(`대응하는 공고 요구`). 대응 요구를 못 적으면 그 경험은 목록에서 뺀다.
- 5개를 억지로 채우지 않는다. 맞는 것이 3개면 3개만 쓴다.

### 서류용과 면접용을 구분한다

기본은 서류(경력기술서·자소서) 기준으로 순위를 매긴다. 둘은 쓰는 카드가 다르다.

| | 경력기술서·자소서 | 면접 |
|---|---|---|
| 단위 | 프로젝트: 기간·역할·산출물·성과가 있어야 한다 | 에피소드: 상황과 판단 과정이면 된다 |
| 맞는 경험 | 독립된 프로젝트로 설명되는 것 | 프로젝트 안의 의사결정, 갈등, 실패 |

프로젝트 안의 에피소드나 소프트스킬 서사는 서류의 단독 항목이 될 수 없다. 산출물과 수치가 없어 얇게 읽힌다. 서류에서는 상위 프로젝트 항목 안에 기술적 실체만 한 줄로 녹인다.

- 경험의 `답할 수 있는 질문`에 인성 질문 유형만 적혀 있으면 면접용 신호다. 서류 순위에 올리기 전에 한 번 더 판단한다.
- 반대로 공고가 협업·조율을 필수 요구경험으로 명시했다면, 그 역량을 커버하는 프로젝트 단위 경험을 찾는다. 소프트스킬 카드를 대신 올리지 않는다.
- 서류에서 뺀 경험은 뺀 이유와 대신 어디에 쓸지를 함께 적는다(`## 서류에서 뺀 경험`의 `쓸 곳`). 그냥 누락시키지 않는다.

### 키워드가 아니라 기술적 실체로 순위를 매긴다

공고 문구와 경험 제목이 겹친다고 상위에 올리지 않는다. 순위를 정하기 전에 두 가지를 확인한다.

1. 경험에 설명할 기술적 내용이 실제로 적혀 있는가. 방법론·과정만 있고 구현 내용(설계 판단, 알고리즘, 구조)이 없으면 서류에서 쓸 수 없다. 특히 전문지식·스킬을 묻는 문항에서는 얇은 카드가 바로 드러난다.
2. 공고 문장을 끝까지 읽었는가. 단어 하나에 앵커링하지 않는다. 예를 들어 "정합성을 자동화된 방식으로 검증하고, 적시성 기준과 이상 탐지 체계로 신뢰를 관리"는 정합성이 아니라 상시 자동 운영 체계를 요구한다. 일회성 검증 경험은 여기 맞지 않는다.

판단이 서지 않으면 수치와 구현 디테일이 있는 쪽을 고른다.

### 자소서 문항이 있으면 문항별로 배치한다

문항마다 요구하는 것이 다르다. 전문지식·스킬을 묻는 문항에 소프트스킬 서사를 쓰지 않는다. 문항 목록을 받았으면 어느 경험을 어느 문항에 쓸지 표로 제시한다. 문항이 입력에 없으면 만들지 않는다.

## 마무리

매칭하면서 "이 경험은 DB에 더 자세히 적혀 있어야 한다"고 느낀 부분을 `경험 보완 제안`과 돌려주는 보고에 쓴다. 공고 매칭은 경험 DB의 빈 곳을 발견하는 가장 좋은 기회다. 다만 공고마다 실제로 강조 가치가 있는 것만 골라 쓴다. 미작성 항목을 매번 나열하지 않고, 우선순위가 애매하면 제시하지 않는다.
