# 산출물 작성 규칙 (자소서·경력기술서)

`doc-writer`가 지키는 형식 규칙과, 메인 세션이 작성자 → 위험검증자 → 서류검토자를 돌리는 절차. 절대 규칙(없는 경험·수치를 만들지 않는다 등)은 이 파일이 아니라 `.claude/agents/`의 에이전트 4개 본문에 각각 있다. 문체·구성 기준(과장 없는 문장, 공고 효용 연결, 하나의 주제)은 `.claude/agents/doc-writer.md`에 있다.

## 자소서는 마크다운을 쓰지 않는다

자소서 본문은 제출 폼에 붙여넣는 순수 텍스트다. 아래를 쓰면 사용자가 직접 지워야 한다.

- `**굵게**`, `## 제목`, 표, 불릿(`-`), 인용(`>`), 구분선(`---`) 전부 금지
- 계층은 번호와 문장으로 표현한다
  - 대제목: `1. 주문 알림 발송 구조 개선`
  - 하위 구분: `첫째, 저장소 접근 계층 추상화`
- 날짜는 `2021년 11월` 형식. `2021.11`이 아니다

## 경력기술서는 마크다운 양식을 따른다 (사용자 결정, 2026-10-27)

경력기술서 파일은 아래 양식의 마크다운이다. 위 자소서의 마크다운 금지는 적용하지 않는다. 아래 기호 말고는 쓰지 않는다 (`**굵게**`, 표, 불릿, 구분선 금지).

- 맨 위에 `# 경력기술서`를 반드시 적는다
- 프로젝트(경험) 구분은 `## 번호. 제목` (예: `## 1. 지표 식별 기준 표준화`)
- 한 구분 안에 프로젝트가 여럿이면 `### 번호) 제목` (예: `### 1) 외부 가격비교 데이터 적재 테이블 설계`)
- 기간과 주요 역할은 제목 바로 아래에 인용 두 줄로 쓴다. 첫 줄 끝에 공백 두 개를 붙여 줄이 나뉘게 한다

  ```
  > 기간: 2021년 11월 ~ 2021년 12월  
  > 주요 역할: SSG.COM 데이터 엔지니어, UV 산출 로직 전수 조사와 표준 식별자 설계
  ```

- 구분 안에 프로젝트가 여럿이면 기간·주요 역할은 `##`가 아니라 각 `###` 아래에 쓴다
- 날짜는 `2021년 11월` 형식. `2021.11`이 아니다
- 서두 문단은 `# 경력기술서` 아래, 마무리 문단은 마지막 구분 뒤에 둔다. 본문은 그대로 줄글이다

## 포트폴리오도 마크다운 양식을 따른다 (사용자 결정, 2026-10-27)

포트폴리오 파일은 마크다운이다. 자소서의 마크다운 금지는 적용하지 않는다. 본문 문장은 그대로 두고 기호만 붙인다.

- 맨 위에 `# 프로젝트 제목`, 그 아래 한 줄로 `개인 프로젝트 포트폴리오 / 이름`
- 절 구분은 `## 번호. 제목`, 개요처럼 번호가 없는 절은 `## 제목`
- 기간·형태·데이터·사용 기술·저장소 같은 항목 나열은 `- 항목: 내용`
- 순서가 있는 단계는 `1.` 번호 목록, 병렬 항목은 `- ` 불릿. 코드·명령·테이블 이름은 `` `코드` ``
- 그 밖의 문단은 줄글 그대로. `**굵게**`, 표, 구분선은 쓰지 않는다
- 날짜는 `2026년 3월` 형식

## 이력서는 예외: 칸 구조와 "- " 기호 (사용자 결정, 2026-10-27)

위 "자소서는 마크다운을 쓰지 않는다"는 자소서 본문에 해당한다. 이력서는 앱의 칸(`documents.data`)에 한 줄씩 넣는 글이고, 앱은 줄 앞에 기호를 그리지 않는다(`styles.css`의 `.rs-li`). 기호는 글에 직접 적혀 있어야 한다.

- 업무 줄은 모두 `- `(하이픈과 공백 하나)로 시작한다. 칸에 넣을 때 그대로 붙여 넣을 수 있게 처음부터 붙여 쓴다. 이미 `1.` 같은 번호가 있는 줄은 `- `를 겹쳐 붙이지 않는다
- 프로젝트가 여럿 든 묶음은 앱의 "프로젝트형 묶음 추가"에 맞춘다
  - 묶음 제목: 묶음의 주제 (예: `지표 표준화와 원천 모델링`)
  - 프로젝트 이름 칸: `프로젝트 이름 (기간)`. 앞에 `- `를 붙이지 않는다 (예: `검색 실적 마트 원천 교체 (2022.06 - 2022.08)`)
  - 그 아래 내용: 한 줄에 하나, 앞에 `- ` (예: `- 마트 grain을 유지한 채 페이지 로드 기반 원천을 API 단위 이벤트 로그로 전환`)
  - 프로젝트 이름을 업무 줄처럼 `- `로 적고 그 아래를 들여 쓴 `  - `로 적지 않는다 (프로젝트 칸을 쓰지 않은 평평한 구조가 된다)
- 프로젝트가 하나뿐이면 "업무 묶음 추가"로 만든다. 묶음 제목에 프로젝트 이름과 기간을 쓰고 그 아래는 `- ` 줄이다
- 회사는 묶음 제목이 아니라 회사 칸(회사 이름 / 기간 / 고용 형태 / 직무)에 넣는다
- 날짜는 이력서에서는 `2022.06 - 2022.08` 형식이다 (`2021년 11월` 규칙은 자소서·경력기술서용)
- 학력(출신 대학)에는 학교 이름과 함께 전공을 반드시 적는다 (사용자 결정, 2026-10-27). 전공은 `profile`의 학력에서 가져오고, 없으면 지어 쓰지 말고 비워 둔 채 알린다

## 문체: AI 티를 지운다

- 한 항목당 2~4문단의 줄글. 짧은 문장을 나열하지 않는다
- 화살표(`→`)로 성과를 요약하지 않는다. 성과도 문단으로 서술한다
- 괄호 주석(`*(...)*`)으로 단서를 달지 않는다. 필요하면 문장 안에 녹인다
- 같은 문장 구조를 반복하지 않는다
- 기술 용어는 처음 나올 때 원어를 병기한다: `AQE(Adaptive Query Execution)`, `듀얼 런(Dual-run)`, `계보(Lineage)`
- 알고리즘·계산 과정을 문장 안에서 단계별로 재현하지 않는다. "무엇을 만들었고 왜" 수준으로 요약하고, 세부 도출 과정(중간 계산 등)은 문항 본문에 풀어 쓰지 않는다. 이런 디테일은 면접에서 질문받았을 때 답하는 용도다

## 문항별 성격을 구분한다

| 문항 | 성격 |
|---|---|
| 경력기술서 | 프로젝트 단위. 기간·역할·문제·해결·성과를 사실 중심으로 |
| 역량/직무수행 이유 | 줄글 에세이. 공고의 핵심 문구 하나를 주제로 잡고 그것을 향해 전체를 구성 |

역량 문항은 경험 나열이 아니다. 공고의 핵심 문구 하나를 주제로 잡고, 서두에 직무관과 주제를 선언한 뒤 경험으로 증명하고 지원 회사에 연결하며 마무리한다. 지원동기 같은 빈출 문항은 사용자가 정한 공식이 [`frequent-questions.md`](frequent-questions.md)에 있다. 해당 문항이면 그 공식을 따른다.

## 갭 고백 섹션은 넣지 않는다

서류에서 먼저 약점을 나열하지 않는다("솔직하게 말씀드리는 부분" 같은 섹션 금지). 없는 경험을 있다고 쓰지 않는 것으로 충분하다. 갭은 공고분석의 `갭`과 `약한 부분`에만 있고 면접 대비용이다.

## 파일 배치

- 본문: `private/drafts/<회사>/<회사>-문항N-주제.md`. 제출 텍스트만 쓴다. 검증 메모를 넣지 않는다 (자유 양식이면 `<회사>-경력기술서겸자기소개서.md`)
- 메모: `private/drafts/<회사>/<회사>-작성메모.md`. 맨 위 `## 지원서 항목`, 근거 매핑표, 판단이 필요한 부분, 의도적으로 쓰지 않은 것, 글자 수, 그리고 메인 세션이 붙이는 `## 검증 기록`·`## 서류검토 기록`
- `private/`는 git이 무시한다. 초안·메모·분석·문체 샘플을 커밋하지 않는다.

## 작성·검증 절차 (메인 세션)

쓴 사람이 자기 글을 검증하면 근거 없는 내용이 걸러지지 않는다. 작성과 검증을 서로 다른 서브에이전트로 나눈다 (`doc-writer`, `risk-checker`, `doc-reviewer`).

메인 세션은 조율자다. 서브에이전트는 다른 서브에이전트를 띄울 수 없고 사용자에게 물을 수도 없으므로, 사용자와 대화하고 서브에이전트를 띄우고 결과를 이어 주는 일을 모두 메인 세션이 한다. 메인 세션은 초안 작성과 검증을 직접 하지 않는다.

0. 작성 전 확인: 메인 세션이 사용자에게 반드시 묻는다. 요청에 이미 들어 있는 것은 다시 묻지 않는다. 답을 받기 전에는 작성자를 띄우지 않는다.
   - 지원서에 어떤 입력 항목이 있는가: 자기소개서 문항이 있는지, 없으면 자유 양식(경력기술서·자기소개서 첨부란)인지
   - 문항이 있으면: 문항 원문 전체(번호 포함)와 문항별 글자 수 제한(공백 포함/제외)
   - 문항이 없으면: 분량 제한, 파일 첨부인지 텍스트 입력인지
   - 어느 공고분석(`jobs`의 id)을 근거로 할지. 공고분석이 앱에 없으면 `job-analyst`부터 하자고 제안한다 (`private/inbox/jobs/`에 쓰고 `/import-jobs`로 앱에 넣은 뒤에야 `job <ID>`로 읽을 수 있다)
   받은 답은 작성자에게 그대로 넘기고, 작성메모 맨 위 `## 지원서 항목`에도 남기게 한다.
1. 작성자(`doc-writer`)가 본문과 작성메모(근거 매핑표 포함)를 쓴다.
2. 새 서브에이전트로 위험검증자(`risk-checker`)를 띄워 판정받는다. 작성자와 같은 컨텍스트를 쓰지 않는다.
3. 메인 세션이 판정 결과 전문을 작성메모의 `## 검증 기록`에 날짜·회차와 함께 붙인다.
4. FAIL이면 판정 결과를 입력으로 작성자가 수정하고 2번으로 돌아간다.
5. 3회차에도 FAIL이면 멈추고 사용자에게 보고한다. 최종 판단은 사용자가 한다.
6. PASS이면 새 서브에이전트로 서류검토자(`doc-reviewer`)를 띄운다. 메인 세션이 결과 전문을 작성메모의 `## 서류검토 기록`에 날짜·회차와 함께 붙인다. 면접 질문 표는 면접 준비에도 쓰므로 지우지 않는다.
7. '보완 권장'이면 검토 결과를 입력으로 작성자가 고친다. 고친 본문은 다시 위험검증자(2번)부터 거친다. 읽기 좋게 고치다 근거 없는 말이 들어가기 쉽다.
8. 서류검토는 최대 2회차. '통과'이거나 2회차에도 '보완 권장'이면 멈추고 사용자에게 보고한다.

규칙:
- 사용자가 직접 수정한 산출물도 사용자가 "검증해줘"라고 하면 2~3번만, "검토해줘"라고 하면 6번만 수행한다. 둘 다면 2번부터.
- 위험검증자 PASS는 사실·수치·형식 확인이다. 서류검토자 통과는 AI 한 명이 읽은 인상이다. 둘 다 통과해도 최종 판단은 사용자가 직접 읽고 한다.
- 서브에이전트에게 넘길 때는 대상 파일 경로(`private/drafts/...`), 공고분석 id, 회차를 적어 준다. 서브에이전트는 `.claude/agents/`의 자기 정의를 이미 따르므로 역할 파일을 읽으라고 시킬 필요가 없다.
- 사용자가 준 피드백 중 다음 글에도 적용할 것은 메인 세션이 날짜와 함께 `.claude/agents/doc-writer.md`의 "유형별 작성 기준"에 더한다.

## 저장 정리

- 공고분석 → `private/inbox/jobs/`에 쓰고 `/import-jobs`로 앱에 넣는다 (시험 실행, 백업, 그다음 사용자가 직접 연 터미널에서 DB 이름을 입력해 저장).
- 초안·작성메모 → `private/drafts/<회사>/` 파일로만 둔다. 앱에는 저장하지 않는다 (자소서를 앱에 넣는 일은 다음 작업이다).
- 사용자가 경력기술서를 앱에 넣고 싶어 하면, 메인 세션이 `app.importers.documents` JSON(앱 서식)으로 바꿔 `--dry-run`까지 하고, 실제 저장은 사용자가 직접 연 터미널에서 하게 한다. 서브에이전트는 저장 명령을 돌리지 않는다.
