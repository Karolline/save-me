### 고치면 좋은 것
- [backend/app/semantic_search.py `post_batch`/`post_with_retry`] `Retry-After`가 숫자이기만 하면 그대로 `sleep`에 넘긴다. 그래서 값에 따라 문제가 생긴다.
  - 음수면 `ValueError`, `inf`면 `OverflowError`가 나는데, 둘 다 `SearchError`가 아니라 traceback으로 끝난다.
  - 아주 큰 값이면 멈춘 것처럼 보이고, `nan`도 걸러지지 않는다.

  정상적인 Voyage 응답에서는 생기지 않을 일이다. `0 <= wait <= 몇 분` 범위가 아니면 21초를 쓰게 막아 두면 좋다.
- [backend/tests/unit/test_semantic_search.py] 진행 표시가 stdout에 섞이지 않는다는 것을 따로 확인하는 테스트가 없다. 지금도 `log`는 stderr로만 쓰고, 출력을 비교하는 기존 테스트로 사실상 막혀 있다. 진행 표시 테스트에 `"임베딩" not in out` 한 줄을 넣으면 의도가 분명해진다.

### 확인한 것
- **묶음별 캐시 저장.**
  - 남의 데이터를 섞지 않는다. `kept`에는 지금 사용자의 지금 조각만 들어가고, 키는 `user_id:experience_id:section`이다.
  - 이미 받은 벡터를 잃지 않는다. 캐시 적중분이 처음부터 `kept`에 있고, 묶음마다 새 벡터를 더해 저장한다.
  - 저장은 임시 파일에 쓴 뒤 `os.replace`로 바꾼다. 중간에 끊기면 임시 파일만 지워지고 전에 쓴 파일은 남는다.
- **이어하기.** 둘째 묶음에서 실패하면 캐시에 첫 묶음 조각만 남는다. 다시 돌리면 남은 조각만 보낸다 (`test_cache_saved_per_batch_and_resumes`).
- **429만 다시 시도.**
  - `RateLimited`는 HTTP 429일 때만 생긴다. 401, 500, 네트워크 오류는 바로 `SearchError`로 끝난다.
  - 다시 시도는 6번이고, 기다리는 시간은 `Retry-After` 또는 21초다.
  - 다 실패하면 지시서 문구 그대로 오류를 내고 종료 코드 1로 끝난다.
  - 질문 임베딩도 같은 다시 시도를 거친다.
- **토큰 기준 묶음.** 글자 수 합 8000 이하, 64개 이하로 묶고, 긴 조각은 혼자 둔다.
- **진행 표시.** stderr에만 찍고, 모두 캐시에 있으면 아무것도 찍지 않는다. 기존 API 오류 테스트를 stderr 마지막 줄로 보게 바꾼 것은 요구와 어긋나지 않는다.
- **기존 테스트 방식 유지.** `embed`를 가짜로 바꾸는 `calls` 고정물이 그대로이고, 남의 데이터 분리 테스트도 남아 있다.
