# 작업: cover-letter (이슈 #22)

## 목표
지원서류 묶음에 네 번째 서류 "자소서"를 더한다. 자소서는 문항을 최대 5개까지 두고, 문항마다 문항 글·글자 수 제한·답변을 적으며, 답변의 글자 수를 입력하는 대로 세어 준다. 자소서가 앱 밖 파일이 아니라 DB에 들어간다.

## 동작
- 서류 종류 `coverletter`(화면 이름 "자소서")가 `resume`, `career`, `portfolio` 뒤에 더해진다. 묶음 화면의 서류 칸은 네 개, 서류 상세 위쪽 서류 전환 탭에도 "자소서"가 보인다 (없는 서류는 기존처럼 "아직 없어요" + [만들기]).
- 자소서를 만들면 문항 없이 빈 자소서가 생기고 문항 하나를 처음부터 보여 준다 (빈 문항 카드 1개, 저장은 입력이 있을 때부터. 구현은 개발자가 정하되 빈 문항이 DB에 저장되지는 않게 하거나, 저장돼도 화면이 어색하지 않게).
- 서류 상세에서 자소서 편집 화면은 `.claude/tasks/cover-letter.mockup.html`(확정 목업)과 같다. 파일을 브라우저로 열어 보고 만든다. 아래는 그 설명:
  - 위쪽 바: [← 묶음] · 서류 전환 탭 · "합계 N자 · N/5문항" · 저장 상태(기존 서류 상세의 "저장됨/저장 중/저장 실패" 표시와 같은 방식) · [자소서 지우기](기존 서류 지우기처럼 확인 후).
  - 왼쪽 문항 목록 사이드바(sticky, 폭 220px): 문항마다 "번호. 문항 글 앞 18자(없으면 '(문항 없음)')"와 오른쪽에 글자 수 (제한이 있으면 `N/제한`). 클릭하면 그 문항 카드로 이동한다. 맨 아래에 "합계 N자 · N/5문항".
  - 오른쪽에 문항마다 카드 하나: 제목 "문항 N"과 오른쪽 위 [✕](문항 지우기, 확인 후 지움: "문항 N을 지울까요?"), "문항" textarea(placeholder "지원서의 문항을 그대로 붙여 넣으세요"), "글자 수 제한 (공백 포함)" 숫자 입력(placeholder "없음", 옆에 "자 · 비우면 제한 없음"), "답변" textarea(placeholder "답변을 쓰세요", 최소 높이 220px), 그 아래 글자 수 줄과 진행 막대.
  - 글자 수 줄: 크게 `공백 포함 글자 수 / 제한자`(제한 없으면 `N자`), 옆에 "공백 제외 N자"(참고), 오른쪽 끝에 "N자 남음" 또는 "N자 초과"(제한 있을 때만). 제한의 90% 이상이면 노랑, 넘으면 빨강(숫자와 문구 모두, 막대 색도 같이). 진행 막대는 제한 있을 때만 차고 100%에서 멈춘다.
  - 글자 수 세기: 공백 포함 = 줄바꿈을 `\n`으로 바꾼 뒤(`\r\n`은 1자) 코드 포인트 수(이모지 1자). 공백 제외 = 공백·줄바꿈을 뺀 코드 포인트 수. 제한 비교는 공백 포함 기준. 이 계산은 `src/lib/`의 순수 함수로 두고 단위 테스트한다.
  - 아래 [+ 문항 추가]: 맨 뒤에 새 문항. 문항이 5개면 비활성이고 옆에 "문항은 최대 5개까지예요." 순서 바꾸기는 없다.
  - 글자 수 제한 입력은 1 이상의 정수만, 비우면 제한 없음.
- 저장은 기존 서류 편집기의 자동 저장(입력을 멈추고 `AUTOSAVE_MS` 뒤, 화면을 떠날 때 마지막 저장, 차례 보내기)과 같은 방식을 따르되 단위는 자소서 전체(문항 목록 통째)다. 서류 전환·묶음으로 돌아가기 전에 저장 안 된 것을 저장한다.
- 묶음 화면의 자소서 칸: 서류 이름 "자소서", "직접 작성 · 고친 날 MM-DD"(기존 칸과 같은 형식), "문항 N개 · 합계 N자", 제한을 넘은 문항이 있으면 "글자 수 초과 N문항"(빨간 pill). 리뷰 칸은 "검토 전" pill만 둔다.
- 자소서는 이번에 리뷰와 연결하지 않는다: 리뷰 작성 양식의 서류 선택지에 자소서가 나오지 않고, 서버가 자소서 덩어리가 든 리뷰를 보내면 422다. 서류 상세의 미리보기(A4)·[PDF로 내려받기]·리뷰 칸은 자소서에서 보이지 않는다 (자소서 편집 화면은 위 목업처럼 한 화면이다). `/print/...`와 서버 PDF 코드(꺼 둠)는 건드리지 않되, 서류 종류가 늘어서 타입 검사가 깨지면 자소서를 제외하도록 맞춘다.
- 서류 묶음 지우기·사용자 삭제 때 자소서 문항도 같이 지워진다(CASCADE).

## 데이터와 API
- 새 테이블 `cover_letter_items` (`app/db.py`, 마이그레이션 Alembic): `id`, `user_id`(users CASCADE, index), `document_id`(documents.id CASCADE, index), `position`(0부터), `question` Text, `char_limit` Integer nullable(없으면 제한 없음), `answer` Text. (document_id, position) 유니크. 자소서의 "서류 한 칸"은 기존 `documents` 행(type=`coverletter`, body는 쓰지 않고 빈 문자열, source `written`)으로 두어 묶음 안의 서류 칸·고친 날·중복 방지가 그대로 쓰이게 한다.
- `DOCUMENT_TYPES`/`DocumentType`에 `coverletter` 추가 (정렬 순서는 맨 뒤). 기존 `documents` 엔드포인트의 의미를 최대한 유지한다. `PUT .../documents/coverletter`(본문 저장)는 쓰지 않는다 → 422. 가져오기(`app/importers/documents.py`)는 자소서를 다루지 않으니 종류 검사만 안 깨지게 한다.
- 새 엔드포인트 (`app/routers/documents.py`, 모두 `current_user`, 남의 것은 404):
  - `GET /api/document-groups/{group_id}/cover-letter` → `{ updatedAt, source, items: [{ question, charLimit, answer }] }` (자소서가 아직 없으면 404 "Document").
  - `PUT /api/document-groups/{group_id}/cover-letter` body `{ items: [{ question, charLimit, answer }] }` → 문항 목록을 통째로 바꾼다(위치는 배열 순서). 문항 5개 초과는 422. `charLimit`은 1 이상 또는 null. 문서의 `updatedAt`을 갱신한다. 자소서가 없으면 404. 응답은 GET과 같은 모양.
  - 만들기·지우기는 기존 `POST/DELETE .../documents/coverletter`를 그대로 쓴다 (만들 때 body는 빈 문자열, 문항 0개).
- `DocumentSlot`(묶음 응답의 서류 칸)에 자소서일 때만 `itemCount`, `totalChars`(공백 포함 합계), `overLimitCount`를 더한다 (그 밖의 서류는 null). 글자 수 계산은 프런트엔드와 같은 규칙(`\r\n`은 1자, 코드 포인트 수)을 서버에도 둔다.
- 경로의 실제 접두사·모델 이름은 `app/routers/documents.py`·`app/models.py`의 기존 것을 따른다. 프런트엔드 서비스 층(`types.ts`의 `SaveMeService`, `httpService.ts`, `mockService.ts`)에 같은 동작을 더하고 mock도 같은 규칙(5개 제한, 중복·연결 규칙, 칸 요약)을 지킨다. 컴포넌트는 `useService()`만 쓴다.

## 끝났다고 보는 조건
- 백엔드: store·API 통합 테스트 — 자소서 만들기(중복 409는 기존 규칙), 문항 저장·조회 왕복(순서·null 제한), 6개 → 422, `charLimit` 0·음수 → 422, 문항 바꿔 저장하면 이전 문항이 사라짐, 자소서 지우면 문항도 사라짐, 묶음 지우면 같이 사라짐, 묶음 응답의 `itemCount/totalChars/overLimitCount`, 리뷰에 자소서 덩어리 → 422, 본문 저장 → 422, **남의 묶음의 자소서 조회·저장·만들기·지우기는 모두 404**. 마이그레이션 테스트(`tests/unit/test_migrations.py`)를 PostgreSQL에서 통과.
- 프런트엔드: 글자 수 순수 함수 단위 테스트 (빈 글, 한글, 이모지, `\r\n`, 공백 제외, 상태 정상/노랑(90%)/빨강), 편집 화면 컴포넌트 테스트 (문항 추가·5개에서 막힘, 지우기 확인, 글자 수 즉시 갱신, 사이드바 표시와 클릭 이동, 자동 저장 호출), 묶음 화면의 자소서 칸, 서비스 mock/HTTP 테스트. 입력 칸 16px 이상 테스트(`styles.css`)가 새 칸까지 통과.
- 개발 서버로 직접 열어 확인하고 보고서에 적는다 (`make run back`, `make run front`, `saveme_dev`).
- 건드린 영역의 테스트, `npm run build`, `npm run lint`가 초록. 전체 테스트는 CI가 한다.

## 화면
- `.claude/tasks/cover-letter.mockup.html` (확정 목업, 이 작업이 병합될 때 지시서·보고서와 함께 지운다). 화면 ①은 묶음 화면의 4번째 칸, 화면 ②는 자소서 편집. 폰트·색은 기존 `styles.css` 토큰(목업이 같은 토큰을 쓴다). 목업의 인라인 CSS를 `styles.css`로 옮길 때 기존 클래스(`.card`, `.btn`, `.pill`, `.link` 등)가 있으면 재사용한다.

## 하지 않을 것
- 모바일 레이아웃·테스트 (AGENTS.md). 문항 순서 바꾸기. 자소서의 리뷰·PDF·인쇄 미리보기. AI 작성(#6).
- 기존 문항 가져오기(`private/drafts/` → DB): 사용자가 직접 앱에 적는다. `private/`는 읽지도 건드리지도 않는다.
- 진짜 DB(`saveme`)에 쓰지 않는다. 마이그레이션은 `saveme_dev`에서만 시험한다.
- 새 의존성 없음.

## 사용자와 정한 것
- 글자 수는 공백 포함으로 제한과 비교하고 공백 제외는 참고로 보여 준다 (사용자 확인).
- 문항 목록 사이드바는 넣는다. 순서 바꾸기는 하지 않는다 (사용자 결정, 2026-10-25).
- 묶음 칸 정보는 문항 수·합계·초과 경고로 충분하다 (사용자 확인).
- 기존 문항 가져오기는 하지 않는다 (사용자가 수기로 입력, 2026-10-25).
- 문항은 서류 하나당 최대 5개.
