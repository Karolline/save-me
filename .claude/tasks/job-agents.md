# 작업: job-agents

## 목표
다른 프로젝트에서 쓰던 취업 역할 에이전트 4개(공고분석가·작성자·위험검증자·서류검토자)를 SaveMe의 `.claude/agents/`로 옮긴다. 에이전트는 DB에 직접 접속하지 않고 `agent_read` 조회 명령으로 사용자의 경험·이력·공고분석을 읽고, 결과는 파일로 남긴다. 이슈 #6의 2단계(1단계: `agent-read`, `import-confirm`은 main에 병합됨).

## 동작

### 에이전트 4개 (`.claude/agents/`, 한국어, frontmatter `model: opus`)
| 파일 | 일 | tools |
|---|---|---|
| `job-analyst.md` | 공고 원문을 경험과 대조해 분석, 회사 동향 조사, 받은편지함 양식 파일 작성 | Read, Grep, Glob, Bash, Write, WebSearch, WebFetch |
| `doc-writer.md` | 자소서·경력기술서 초안과 근거 매핑표 작성 | Read, Grep, Glob, Bash, Write |
| `risk-checker.md` | 초안을 경험 원문과 대조해 PASS/FAIL 판정 (파일 수정 안 함) | Read, Grep, Glob, Bash |
| `doc-reviewer.md` | 면접관으로 읽고 이해도·면접 질문·한 줄 소개를 냄 (파일 수정 안 함, 경험 안 읽음) | Read, Grep, Glob, Bash |

- 원본은 `N:\개인\취준자료\2025-2026\SaveMe\AI지침\역할\{공고분석가,작성자,위험검증자,서류검토자}.md`와 `AI지침\규칙\{공고매칭,산출물작성,빈출문항}.md`, 같은 폴더 위 `AGENTS.md`의 절대 규칙·프레이밍 주의·본인이 하지 않은 일이다. **읽기만 한다 (고치지 않는다).** 옮길 때 구조·판정 항목·출력 형식·완료 기준은 가능한 그대로 살리고, 아래 "바꾸는 것"만 바꾼다.
- 공통으로 길어지는 규칙(공고매칭 절차·핏 평가 기준·성향 적합도 루브릭·출력 형식, 산출물 형식 규칙, 빈출문항 공식)은 `docs/agent-rules/` 아래 한국어 파일로 둔다(예: `job-matching.md`, `writing-rules.md`, `frequent-questions.md`). 에이전트는 시작할 때 필요한 것만 읽는다. **절대 규칙은 이 파일들에 두지 않고 에이전트 4개 본문에 각각 그대로 넣는다** (약하게 줄이지 않는다):
  - 조회 결과에 없는 경험·수치를 만들지 않는다. 근거가 없으면 "없다"고 말한다. 그럴듯한 제안은 되지만 근거 경험(ID)을 함께 제시한다. DB에 "30% 개선"이 없으면 30%라고 쓰지 않는다.
  - 경험의 예상 질문과 답변, 면접후기의 AI 첨언·미분류는 서류의 근거로 쓰지 않는다 (조회 기본 출력에는 없고 `--include-reference`에서만 "⚠ 근거 아님"으로 나온다. 에이전트는 서류 작업에서 `--include-reference`를 쓰지 않는다).
  - 경험의 프레이밍 주의를 따른다. 본인이 하지 않은 일("본인이 수행하지 않은 영역", 팀 성과)은 담당 범위를 구분해 쓴다.
  - 후기의 "다시 답한다면"은 실제로 한 답이 아니라는 점을 구분한다.

### 바꾸는 것 (옛 프로젝트의 흔적 정리)
- 옛 `나/경험/…`, `나/프로필/…`, `AI산출물/…` 파일 링크와 "`사람확인` 프론트매터"는 없앤다. 대신 조회 명령을 쓴다:
  `uv run python -m app.agent_read experience-index | experience <ID> | profile | personality | reviews | jobs | job <ID>` (`backend/` 안에서). 가져온 분석·서류의 "사람 확인"은 DB의 확인 플래그(가져온 건 N)가 대신한다. 에이전트는 확인 상태를 Y로 바꾸지 않는다(바꿀 수단도 없다).
- 분석 HTML 파일과 대시보드 HTML 행 추가는 하지 않는다 (사용자 결정: 앱의 공고분석 화면이 보여 준다). 옛 프로젝트의 지원 이력·파일 폴더(`미지원/`·`지원완료/`) 얘기도 뺀다.
- **공개 저장소라 개인 정보를 넣지 않는다.** 원본에 있는 사용자의 실제 회사명·서류 파일 경로·면접 일화(예: 특정 회사의 탈락 사례, 샘플 서류의 회사명, "42dot류" 같은 실명 예시)는 옮기지 않고, 필요하면 일반적인 말로 바꾼다(예: "순수 R&D 조직"). 옮긴 뒤 `Grep`으로 원본의 고유명사가 남지 않았는지 확인한다.

### 조회에 필요한 `agent_read` 추가 (백엔드 코드)
1. **`job <ID>`**: 공고분석 한 건의 전체를 마크다운으로 (회사·직무·분석일·확인 여부, 한 줄 결론, 지원 조건, 요구사항과 충족도·근거 경험·주의, 핏 평가, 성향 적합도, 부각할 경험, 회사 동향, 기타 메모, 공고 원문). 기존 `jobs`(목록)에는 이미 있는 id를 쓴다. 없는 id는 `경험 id`와 같은 방식으로 안내하고 종료 코드 1. `docs/job-inbox.md`의 양식 순서를 따른다.
2. **`job <ID> --reader`**: 면접관 시점용. **공고 원문과 회사 동향만** 나온다 (서류검토자가 쓴다). 그 밖의 칸(핏, 근거 경험, 부각할 경험 등)은 나오지 않는다.
3. **조회 DB 고르기**: 환경 변수 `AGENT_READ_DATABASE_URL`이 있으면 `agent_read`는 그것을 쓰고, 없으면 지금처럼 `DATABASE_URL`, 그것도 없으면 `saveme_dev`. `.claude/settings.json`에 `"env": {"AGENT_READ_DATABASE_URL": "postgresql://saveme:saveme@127.0.0.1:5442/saveme"}`를 넣어, 에이전트가 허용 규칙(`uv run python -m app.agent_read*`)에 걸리는 평범한 명령만 쳐도 **진짜 데이터**를 읽게 한다. `DATABASE_URL`을 쓰지 않는 까닭: 세션 전체가 그 값을 물려받아 개발 서버·마이그레이션·테스트가 진짜 DB를 건드릴 수 있다. 이 변수는 `agent_read`만 읽는다. 조회는 여전히 쓰지 않고 트랜잭션을 되돌린다.
4. `agent_read` 첫 줄(조회 중인 DB 이름: 예 `saveme`)을 출력 맨 위에 한 줄로 보인다("조회 DB: saveme"). 에이전트와 사용자가 어느 DB를 읽었는지 알 수 있어야 한다.
5. 면접후기의 면접관 말·꼬리질문·개요는 지금처럼 기본 출력에서 제외하고 이번에 더하지 않는다.

### 에이전트별 동작
- **공통 규칙**: 에이전트는 서브에이전트라 사용자에게 물을 수 없다. 모자란 입력(지원서 항목, 공고 원문 등)이 있으면 추측하지 말고 "무엇이 없다"고 보고하고 끝낸다. 에이전트는 **실제 저장 명령(`app.importers.*` `--dry-run` 없이)을 돌리지 않는다.** `--replace-verified`를 쓰지 않는다. frontmatter에 `permissionMode`를 주지 않는다 (`bypassPermissions` 등 넓은 권한 금지).
- **job-analyst**: 입력은 공고 원문(텍스트 또는 URL; URL이 실패·부실하면 추측하지 말고 멈춰 보고). 먼저 `profile`, `experience-index`, `jobs`(이미 한 분석인지 확인)를 보고, 후보 경험만 `experience <ID>`로 연다. 근거는 상황/과제/행동/결과 본문에서만. 분석을 `docs/job-inbox.md` 양식 그대로(제목 글자·순서, 고르는 값, 빈 섹션은 제목째 생략, `공고 원문` 맨 끝) `private/inbox/jobs/YYYY-MM-DD-<회사>-<직무>.md`에 쓴다. 회사 동향은 `WebSearch`/`WebFetch`로 조사해 `## 회사 동향`에 `docs/job-inbox.md`의 "회사 동향 쓰는 법"대로(출처 이름·날짜·링크, 어필 포인트의 근거 경험, 자료가 없으면 `자료 없음`). 이미 같은 (회사, 직무) 분석이 앱에 있으면 사용자에게 알린다(가져오기는 덮어쓰지 않으므로 앱에서 지우거나 `--replace`). 이 파일 말고는 어떤 파일도 쓰지 않는다. 돌려줄 것: 저장 경로, 핏·성향 한 줄, 부각할 경험, 회사 동향 한 줄, 사용자 확인 필요, 경험 보완 제안. 마지막에 "다음: 메인 세션에서 `/import-jobs`"를 안내한다 (에이전트는 가져오기를 돌리지 않는다).
- **doc-writer**: 입력으로 지원서 항목(문항형이면 문항 원문 전체·글자 수, 자유 양식이면 분량·형식)과 공고분석 id를 받는다. 없거나 불분명하면 "지원서 항목 정보가 없다: (빠진 것)"이라고 보고하고 아무것도 쓰지 않는다. `job <ID>`(부각할 경험 순위, 회사 동향 어필 포인트 포함), 필요한 `experience <ID>`, 문항이 빈출문항이면 `docs/agent-rules/frequent-questions.md`의 공식을 따른다. 문체 기준: 원본의 장점 3가지(과장 없이 간결 / 공고 효용 연결 / 하나의 주제)와 구성 틀, "유형별 작성 기준"(꼬리 문장으로 다른 경험 끼워 넣지 않기 등)은 그대로 옮긴다. 합격 서류 샘플은 **`private/style-samples/`(git이 무시, 사용자가 채움)**의 파일을 읽는다. 폴더가 없거나 비었으면 요약 기준만 따르고 "문체 샘플이 없어 기준만 따랐다"고 보고한다. 샘플은 문체·구성의 기준일 뿐 사실의 근거가 아니다. **다른 사람이 쓴 글(파일 이름이 `타인참조자료-`로 시작하는 파일)도 같은 폴더에 있다. 이 글은 사용자 본인에게 없는 장점을 배우는 가이드로 쓴다**: 작성자는 본인 글 샘플을 먼저 읽고 본인 장점을 파악한 뒤, 타인 글에서 본인 글에 없는 장점(구성, 문장 호흡, 서두·맺음 방식 등)을 뽑아 작성메모에 `## 참고한 타인 글의 장점`으로 "무엇을, 어느 문단의 어떤 점을" 적고 초안에 반영한다. 타인 글의 경험·사실·수치·고유한 표현(문장)은 옮기지 않는다. 사실은 늘 `experience`에서만 가져온다. 출력: `private/drafts/<회사>/<회사>-문항N-주제.md`(제출용 순수 텍스트, 마크다운 금지·날짜 `2021년 11월` 형식 등 원본 `산출물작성.md`의 형식 규칙)와 `<회사>-작성메모.md`(맨 위 `## 지원서 항목`, 근거 매핑표 — 근거 칸에는 경험 ID와 섹션, 회사 사정은 `공고분석 회사 동향 (출처)`, 판단이 필요한 부분, 의도적으로 쓰지 않은 것, 글자 수). 위험검증자 FAIL이면 FAIL 항목만 고치고 근거 없는 주장은 돌려 쓰지 말고 삭제, 서류검토자 '보완 권장'이면 우선 고칠 것부터(경험 본문에 없는 내용은 채우지 않고 판단 필요에 남김). 스스로 검증 통과를 선언하지 않는다.
- **risk-checker**: 초안 본문과 근거 매핑표(찾는 용도로만), 본문이 언급하는 `experience <ID>` 원문, `profile`(개발 프로세스, 근거 없는 영역), 공고분석(`job <ID>`)을 보고 판정한다. 판정 항목 4개(사실 근거·수치·담당 범위/프레이밍·형식), "하나라도 FAIL이면 전체 FAIL", 출력 형식, 완료 기준은 원본 그대로. 파일을 고치지 않는다. 확인한 경험 ID를 적는다.
- **doc-reviewer**: 초안 본문(작성메모의 문항 원문·글자 수만 허용)과 `job <ID> --reader`(공고 원문+회사 동향)만 본다. **`experience`, `profile`, 근거 매핑표를 읽지 않는다.** 검토 항목 3개와 출력 형식, "통과/보완 권장" 기준, 칭찬 생략·문장을 대신 써 주지 않기는 원본 그대로. 파일을 고치지 않는다.

### 역할 흐름과 조율
- 흐름은 작성자 → 위험검증자 → 서류검토자. **조율은 메인 세션이 한다** (서브에이전트는 다른 서브에이전트를 못 띄운다). 원본 `산출물작성.md`의 0~8단계(작성 전 확인, 위험검증자 최대 3회차, 서류검토자 최대 2회차, 보완 후 위험검증자부터 다시, 사용자가 고친 서류의 "검증해줘/검토해줘" 처리)를 메인 세션용 절차로 `docs/agent-rules/writing-rules.md`에 쓴다. 메인 세션이 작성메모의 `## 검증 기록`·`## 서류검토 기록`에 결과를 붙인다.
- 저장 정리:
  - 공고분석 → `private/inbox/jobs/`에 쓰고 `/import-jobs`로 앱에 넣는다 (시험 실행 → 백업 → 사용자가 직접 연 터미널에서 DB 이름 입력).
  - 초안·작성메모 → `private/drafts/<회사>/` 파일로만 둔다. **이번 작업에서 앱에 저장하지 않는다.** 경력기술서·자소서를 앱에 넣는 일(서류 종류 '자소서' 추가, 순수 텍스트와 앱 서식의 변환)은 다음 작업이다. 사용자가 경력기술서를 앱에 넣고 싶어 하면 그때 메인 세션이 `app.importers.documents` JSON(앱 서식)으로 바꿔 `--dry-run`까지 하고 실제 저장은 사용자가 직접 연 터미널에서 하게 한다는 한 줄만 `docs/agent-rules/writing-rules.md`에 적는다.
- `private/`는 git이 무시한다. 초안·분석·샘플을 커밋하지 않는다.

### 문서
- `AGENTS.md`의 "에이전트와 스킬" 절에 한 줄 안내를 더한다 (이름 4개, 조회는 `agent_read`, 저장은 `/import-jobs`와 사용자 터미널, 상세는 `docs/agent-rules/`). 한국어. 이 규칙 전에 쓴 영어 부분은 고치지 않는다.
- `AGENTS.md`의 "에이전트의 조회" 항목에 `job <ID>`, `AGENT_READ_DATABASE_URL`, 기본이 진짜 DB `saveme`를 읽는다는 점을 한 줄 고친다.
- `docs/testing.md` 표에 새 테스트 파일을 더한다.

## 데이터와 API
없음 (DB·마이그레이션·HTTP API 변경 없음). `agent_read` 하위명령 `job`과 환경 변수 `AGENT_READ_DATABASE_URL`만 더한다.

## 사용자와 정한 것
- 이슈 #6 (1단계 `agent-read`, `import-confirm`은 main에 병합됨, 릴리즈 전). 에이전트 이름: `job-analyst`, `doc-writer`, `risk-checker`, `doc-reviewer`.
- 사용자의 권한 모드는 auto라서 권한 규칙만으로 확인을 보장할 수 없다. 저장 막기는 코드(`import-confirm`)가 맡는다. 에이전트는 실제 저장을 돌리지 않고 `--dry-run`까지만 하고 메인 세션에 보고한 뒤, 사용자가 직접 연 터미널에서 실행한다.
- 서류는 앱에 저장하는 것을 지향하되("둘 다 앱에") 자소서 종류 추가가 큰 작업이라 **나눈다**: 이번엔 초안·작성메모를 `private/drafts/`에 파일로만, 앱 저장은 다음 작업.
- 타인 글(`타인참조자료-…`)은 사용자가 본인에게 없는 장점을 배우려고 넣은 것이다(2026-10-25). 샘플 제외가 아니라 "장점만 뽑아 쓰고 내용은 옮기지 않는다".
- 문체 샘플(합격 서류)은 `private/style-samples/`에 사용자가 복사해 두고 작성자가 읽는다. 에이전트 파일에는 장점 요약만, 회사명·경로는 넣지 않는다.
- 조회 DB: env로 고정. 단 이름은 `DATABASE_URL`이 아니라 `agent_read`만 읽는 `AGENT_READ_DATABASE_URL` (세션 전체가 진짜 DB를 가리키는 사고를 피하려고 기획자가 바꿈).
- 분석 HTML·대시보드는 만들지 않는다.
- 후기 꼬리질문은 조회에 더하지 않는다.
- 역할 흐름은 작성자 → 위험검증자 → 서류검토자, 조율은 메인 세션. 위험검증자 3회, 서류검토자 2회 한도는 원본 그대로.
- 옛 프로젝트 파일은 읽기만 한다.
