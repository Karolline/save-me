# 작업 기획

개발자 에이전트는 일하는 동안 사용자에게 물을 수 없다. 그래서 모든 질문은 여기서 먼저 답을 받는다. 결과물은 사용자 눈에 보이는 것은 개발자가 짐작할 일이 없을 만큼 완전한 작업 지시서다.

## 1. 요청 이해

- 할 일 목록은 기획안(`tech 기획안.md`) 7절의 만드는 순서다: 체크 안 된 다음 단계, 그리고 "MVP 이후"와 "나중에 할 일". 인자가 비어 있으면 다음 단계들을 선택지로 보여준다.
- 기획안과 목업은 통째로 읽지 않는다 (기획안 75KB, 목업 300KB). `AGENTS.md`의 "기획안·목업 요약"으로 먼저 판단하고, 필요한 부분만 `Grep -n`으로 줄을 찾아 `Read`의 `offset`/`limit`로 읽는다. 한 대화에서 이미 읽은 부분은 다시 읽지 않는다.
  - 기획안: 작업이 건드리는 절만 (4.2 S2의 화면 명세, 5.13의 데이터 모델, 사용자 분리는 5.3).
  - 목업(`mockup/saveme-mvp.html`): `const SCREENS`에서 화면 id를 찾고, 그 화면을 그리는 `view…` 함수와 CSS 영역만 읽는다. 이미 만든 화면은 `frontend/src` 코드가 기준이다.
  - 그 밖에 `AGENTS.md`와 작업이 건드리는 코드(화면, 서비스, store, 모델, `openapi.yaml`)를 읽어서, 질문이 진짜 빈틈에 대한 것이 되게 한다.
- 목업은 확정이다 (기획안 4.1 "확정"): 화면은 목업과 같아야 한다. 목업과 기획안이 어긋나거나 목업이 어떤 상태를 빠뜨렸으면 2단계에서 물을 질문이다.
- 단계가 사용자의 기존 데이터 가져오기로 끝나면 (기획안 7, "내 기존 데이터 넣기") 지시서에 가져오기 코드를 넣고, 2단계에서 사용자와 원본 파일을 함께 읽을 계획을 세운다.

## 2. 질문

사용자에게 (한국어로, 쉽게. 사용자는 백엔드 전문가가 아니다) 사용자가 보는 것이나 저장되는 것을 바꾸는 모든 것을 묻는다. 예:

- 목업에 없는 상태, 정확한 한국어 글자와 메시지;
- 예외 상황 (아무것도 안 적었을 때, 못 찾았을 때, 아주 긴 글);
- 새 칸을 위해 기존 데이터에 필요한 것 (사용자의 진짜 데이터는 `saveme`에 있고 마이그레이션된다);
- 기획안과 어긋나는 것 (사용자가 바꾸기로 하지 않는 한 기획안이 이긴다. 바꾸면 지시서에 기획안 수정을 한국어로 넣는다).

선택지가 분명하면 AskUserQuestion을 쓰고, 추천을 맨 위에 둔다. 코드, 목업, `AGENTS.md`로 정할 수 있는 것은 묻지 않는다. 사용자에게 보이는 것 중 열린 것이 없을 때까지 묻는다.

**릴리즈 태그 정하기.** 현재 버전을 찾고 (`git tag --list "v*" --sort=-v:refname`의 최신 태그와 `backend/pyproject.toml`), `docs/versioning.md`로 올릴 자리를 고르고, 추천을 맨 위에 두고 옵션마다 한국어 한 줄 이유를 붙여 묻는다 (예: "새 메뉴라 MINOR: v0.1.0 → v0.2.0").

## 3. 화면 보여주기 (목업과 다를 때)

확정 목업이 모든 상태를 이미 보여주면 지시서가 목업을 가리키고 이 단계는 건너뛴다. 아니면 지시서를 쓰기 전에 새로운 상태나 바뀐 상태를 보여준다:

- 스크래치패드 폴더에 `mockup-<짧은 이름>.html` 파일 하나를 만든다. 진짜 앱처럼 보이게: `frontend/src/styles.css`의 CSS를 인라인하고, 마크업과 클래스 이름은 진짜 컴포넌트나 목업에서 복사하고, 그럴듯한 지어낸 한국어 데이터를 쓴다. PC 폭과 휴대폰 폭(390px) 틀을 나란히, **지금**과 **바뀐 뒤**. 정적으로.
- `artifact-design` 스킬을 불러온 뒤 Artifact 도구로 올린다 (비공개, `icon: "design"`). 사용자가 휴대폰에서도 열 수 있다. 사용자가 만족할 때까지 고쳐서 다시 올린다.

## 4. 지시서 쓰기

스크래치패드 폴더에 `task-<짧은 이름>.md`로 저장하고 사용자에게 보여준다. 한국어로 쓰고, 화면 글은 나올 모양 그대로 적는다.

```markdown
# 작업: <이름>

## 목표
<한두 문장: 사용자가 얻는 것>

## 동작
- <사용자가 보거나 할 수 있는 것 하나하나, 정확한 한국어 글자와 메시지>
- <예외 상황과 그때 일어나는 일>

## 데이터와 API
- <새 테이블·칸 (user_id 포함), 엔드포인트, 마이그레이션. 없으면 "없음">

## 끝났다고 보는 조건
- <확인할 수 있는 결과. 있어야 할 테스트 포함 (남의 데이터는 404 테스트 포함)>

## 화면
- <목업 경로와 그 안의 화면 id (예: SCREENS "reviews", "review-edit"), 새 목업 링크가 있으면 그것도>. 똑같이 만든다.

## 하지 않을 것
- <하지 말 것>

## 사용자와 정한 것
- <2단계의 답 하나하나>

## 릴리즈
- 버전 vX.Y.Z (<MAJOR|MINOR|PATCH>: <이유>). 버전을 올리거나 `CHANGELOG.md`를 고치지 않는다: 병합한 뒤 메인 세션이 한다.
```

사용자에게 지시서를 한국어로 요약해 주고 분명한 OK를 받는다. 동의할 때까지 고친다.

## 5. 넘기기

OK를 받으면 Agent 도구로 개발자 에이전트를 띄운다: `subagent_type: "developer"`, `isolation: "worktree"`, `run_in_background: true`, 프롬프트는 지시서 전체. 돌고 있다고 사용자에게 한 줄로 알린다.

## 6. 개발자가 끝나면

1. 보고를 짧은 한국어로 전한다: 한 일, 스스로 정한 것, 멈췄다면 질문. 질문은 사용자와 답을 정하고, 같은 에이전트에게 SendMessage로 보낸다.
2. 브랜치에 리뷰어 에이전트(`subagent_type: "reviewer"`)를 돌린다. 브랜치 이름, worktree 경로, 지시서를 준다. 꼭 고칠 지적은 개발자에게 돌려보내고 다시 리뷰한다.
3. `main`에 병합하면 사용자의 main 브랜치가 바뀌므로 먼저 묻는다. OK면: 저장소 맨 위에서 `main`에 `git merge --ff-only <브랜치>` (`main`이 움직였으면 먼저 worktree에서 rebase하고 테스트를 다시 돌린다), `main`에서 모든 테스트를 돌리고, worktree를 지우고 브랜치를 지운다. push하지 않는다.
4. 지시서의 버전을 `docs/versioning.md`의 "Releasing a version"에 따라 릴리즈하고, 사용자에게 버전과 이유를 한국어 한 줄로 알린다.
5. 돌고 있는 앱에 반영하는 법을 알려준다: `scripts/update.ps1` (백업하고, 다시 빌드하고, 마이그레이션한다). 단계에 데이터 가져오기가 있으면 `docs/local-operations.md`대로 먼저 `saveme_dev`에 돌리고, 사용자가 화면을 확인하고, (백업 후) `saveme`에 돌린다.
6. 기획안 7절에서 그 단계에 체크 표시를 한다.
