# 작업 진행 (진행자)

단계를 이어 주는 일만 한다. 각 단계의 세부는 그 단계의 스킬·에이전트 파일이 정한다: 기획은 `plan-task`, 구현은 `developer`, 리뷰는 `reviewer`, 병합과 릴리즈는 `publish-task`. 단계끼리는 자동으로 이어지지 않고 이 스킬이 하나씩 부른다. 단계 사이의 내용은 `.claude/tasks/`의 파일(지시서 `<이름>.md`, 개발자 보고 `<이름>.report.md`, 리뷰 보고 `<이름>.review.md`)로 넘기므로, 세션이 끊겨도 같은 이름으로 다시 부르면 이어 갈 수 있다.

**이 세션을 개발자와 리뷰어가 끝날 때까지 닫거나 `/clear`하지 않는다.** 백그라운드 에이전트가 끝났다는 알림은 띄운 세션으로만 온다. 사용자가 세션을 닫았다면 `/run-task <이름>`을 다시 부르면 된다.

## 0. 어디까지 했는지 보기

인자가 지시서 이름이면(`.claude/tasks/<이름>.md`가 있으면) 아래로 상태를 보고 해당 단계부터 이어 간다. 아니면 새 작업이다: 1단계부터.

| 상태 | 확인 | 이어 갈 곳 |
|---|---|---|
| 지시서 없음 | `.claude/tasks/<이름>.md` 없음 | 1 기획 |
| 개발자가 안 돌았음 | `git worktree list`에 이름과 맞는 worktree 없음 | 2 개발 |
| 개발자 도는 중 | worktree는 있는데 `.report.md` 없음 | 알림을 기다린다 (이미 끝났는데 알림이 없으면 사용자에게 알리고 개발자를 다시 띄울지 묻는다) |
| 개발자가 멈춤 | `.report.md`가 질문을 담고 있음 | 2 개발 (질문 처리부터) |
| 리뷰 전 또는 낡음 | `.review.md` 없음, 또는 "리뷰한 커밋" 뒤에 `.review.md` 말고 다른 파일을 바꾼 커밋이 있음 (`git diff --name-only <리뷰한 커밋> <브랜치>`) | 3 리뷰 |
| 리뷰 끝 | 위에 해당하지 않음 | 4 넘기기 |

## 1. 기획

`plan-task` 스킬을 Skill 도구로 부른다 (인자: 만들 것). 사용자와의 질문, 지시서 쓰기, OK 받기, 기획 시간 기록은 그 스킬이 한다. 끝나면 `.claude/tasks/<이름>.md`가 main에 커밋돼 있다. plan-task는 개발자를 띄우지 않는다: 띄우는 건 다음 단계에서 이 스킬이 한다.

## 2. 개발

개발자 에이전트를 띄운다: `subagent_type: "developer"`, `isolation: "worktree"`, `run_in_background: true`, 프롬프트는 지시서 전체. 돌고 있다고 사용자에게 한 줄로 알리고, 이 세션을 열어 둬야 한다고 함께 말한다. 그리고 끝났다는 알림을 기다린다.

알림이 오면 worktree의 `.claude/tasks/<이름>.report.md`를 읽고 짧게 전한다: 한 일, 스스로 정한 것, 멈췄다면 질문.

- **멈췄으면** 질문을 사용자와 답으로 정하고, 답을 지시서의 "사용자와 정한 것"에 더해 main에 커밋한 뒤 개발자를 같은 브랜치에서 다시 띄운다 (`subagent_type: "developer"`, 백그라운드, 프롬프트: 지시서 경로와 브랜치·worktree 경로, 답). 다시 끝나면 이 단계를 되풀이한다.
- **끝났으면** 3단계로.

## 3. 리뷰

리뷰어 에이전트를 띄운다: `subagent_type: "reviewer"`, 프롬프트에 브랜치 이름, worktree 경로, 지시서 경로. 리뷰어는 읽기만 하고 파일을 쓰지 못하므로 결과는 이 스킬이 파일로 남긴다. 부르기 직전과 끝난 직후에 시각을 기록한다 (저장소 맨 위에서. 고친 뒤 다시 리뷰하면 이 짝이 또 쌓이고 보고서가 더한다):
`powershell -NoProfile -File scripts/measure.ps1 -Name <이름> -Stage review -Mark start` / `... -Mark end`

리뷰어가 돌아오면 그 보고를 worktree의 `.claude/tasks/<이름>.review.md`에 그대로 저장하고, 맨 위에 `리뷰한 커밋: <브랜치 끝의 git 해시>` 한 줄을 더해 브랜치에 커밋한다 ("리뷰 보고서 추가"). `publish-task`가 병합할 때 지시서·개발자 보고와 함께 지운다.

보고에 "꼭 고칠 것"이 있거나 결과가 "고친 뒤 합치기"나 "다시 작업 필요"이면 **자동으로 개발자를 다시 띄우지 않는다.** 보고를 한국어로 짧게 전하고 사용자에게 어떻게 할지 묻는다 (AskUserQuestion, 추천을 맨 위에):

- 개발자를 다시 띄워 고치기: 지적을 프롬프트에 담아 같은 브랜치에서 다시 띄우고, 끝나면 이 3단계를 다시 한다.
- 그대로 두고 병합으로 가기: 4단계로 (지적은 `.review.md`에 남아 있어 퍼블리셔가 병합 전에 다시 보여준다).
- 여기서 멈추기.

직접 고치지 않는다.

## 4. 넘기기

`.review.md`가 있고 사용자가 병합으로 가기로 했으면(또는 "합쳐도 됨"이면), 병합을 이 세션에서 이어 갈지 묻는다 (AskUserQuestion):

- **이 세션에서 이어서**: `publish-task` 스킬을 Skill 도구로 부른다 (인자: 이름). 번거로움이 없다.
- **`/clear`하고 `/publish-task <이름>`**: 병합 단계의 컨텍스트를 짧게 두려는 선택. 이 세션이 할 일은 끝났다고 알리고 끝낸다.

병합은 `main`을 바꾸므로 `publish-task`가 그 안에서 한 번 더 묻는다.

병합 전에 작업 브랜치의 CI가 초록이어야 한다. 리뷰 보고서까지 커밋했으니, 사용자에게 지금 `git push origin <브랜치>`로 브랜치를 올리면 어느 쪽을 고르든 그동안 CI가 돌아 기다림이 줄어든다고 알린다 (push는 사용자만 한다). `publish-task`가 CI를 확인한다.
